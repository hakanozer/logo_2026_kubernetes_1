Ön analiz ile kod arasındaki farklar

  1. Compose uygulama servislerini başlatmıyor. docker-compose.yml sadece Redis, Kafka/Zookeeper, Elasticsearch/Kibana/Logstash ve yardımcı UI servislerini içeriyor. m01’de altyapı Compose ile, uygulamalar servis klasörlerindeki Maven Wrapper ile başlatılır.
  2. Spring Boot sürümü aynı değil. Gateway, Order, Payment ve Notification POM’ları 4.0.6; Inventory POM’u 3.5.3. Çocuk POM’lar Java 17 derlemesi ister; kökteki ayrı/bağımsız POM Java 24 source/target tanımlar ve multi-module aggregator değildir. Servislerin kendi POM ve Dockerfile’ları esas alınır. Tüm wrapper’lar Maven 3.9.15 dağıtım URL’sini gösteriyor.
  3. Payment ölçekleme: Topic kodda açıkça yaratılmıyor; broker’da auto-create açık, Kafka varsayılan partition ayarı değiştirilmediyse yeni topic tek partition olur. Önce --describe ile doğrulayın; m03’te 3 partition’lı topic için Job uygulanır. Consumer kodu custom factory kullanıyor, concurrency’yi açıkça atamıyor; partition sayısı kadar aktif tüketici sınırı ve uygulama concurrency’si ayrı kavramlardır.
  4. Event gecikmesi: Payment consumer işlem başına 3 saniye bekliyor. Order producer callback’inde de 3 saniye uyku bulunur. Bu, laboratuvar simülasyonudur; throughput testinde etkisini ayrıca not edin.
  5. Kubernetes altyapısı durumsuz. Compose named volumes içerir; referans k8s/infrastructure.yaml Redis/Kafka/Zookeeper/Elasticsearch’i Deployment ve disk mountsuz çalıştırır. Uygulama Order verisi ise emptyDir kullanır. Bu eğitim bunları bilinçli olarak iyileştirir.
  6. Gözlemlenebilirlik farkı: Compose Logstash’i ayağa kaldırır ama K8s manifestlerinde Logstash yoktur. Inventory Logback appender’ı doğrudan Elasticsearch’e sabit localhost URL’siyle yazar; Pod içinde localhost kendi Pod’udur.
  7. Referans manifest sınırları: `k8s/` içinde probe/resources/Ingress/NetworkPolicy/Quota/PVC yok; servis tipleri varsayılan ClusterIP ve gateway port-forward ile açılır. Env düz metindir; app image’ları `logo/*:latest`, `imagePullPolicy: Never` şeklinde.
  8. HTTP test kapsamı: Payment ve Notification portu bildirilmiş olsa da controller yok; gateway’den bu yollara proxy yapılması başarılı REST API anlamına gelmez.
Uygulama kurgusu: App endpoint’lerini doğrularken Inventory `/inventory/list`, Order `/order/orderList` ve Order create POST’ini kullanın. Payment/Notification için Kafka/log ve process health’i doğrulayın; mevcut kodda olmayan HTTP davranışını göstermeyin.

Hazırlık · eğitmen onayı bekleyen öneri diff’leri

Aşağıdaki örnekler eğitim öncesi öneridir; bu çalışma kapsamında uygulama kodu değiştirilmemiştir. Özellikle sağlık/metrics uçlarının açılması ve güvenlik varsayılanları proje sahibinin onayından sonra ayrı değişiklik olarak ele alınmalıdır.

A · Inventory Logback Elasticsearch URL’sini dışarıdan verilebilir yap

- <url>http://localhost:9200/_bulk</url>
+ <springProperty scope="context" name="ES_LOG_URL"
+                  source="ELASTICSEARCH_LOG_URL"
+                  defaultValue="http://localhost:9200/_bulk"/>
+ <url>${ES_LOG_URL}</url>

Kubernetes ortamında değer, http://elasticsearch:9200/_bulk olmalı; appender hatalarının uygulama başlatmasını etkileyip etkilemediği ayrıca denenmelidir.

B · Beş servise Actuator ve Prometheus exporter ekle

+ <dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
management.endpoints.web.exposure.include=health,info,prometheus
management.endpoint.health.probes.add-additional-paths=true

Önerilen endpoint’ler: /actuator/health/liveness, /actuator/health/readiness, /actuator/prometheus. Yetkisiz erişim ve sürüm uyumluluğu test edilmeden tüm endpoint’leri açmayın.

C · Beş image’ı root olmayan UID ile çalıştır

- COPY --from=builder /app/target/*.jar app.jar
+ COPY --from=builder --chown=10001:10001 /app/target/*.jar app.jar
+ USER 10001:10001

JRE katmanındaki dosya izinleri ve volume yazma yolları (özellikle Order /data) test edilmelidir.

D · README’de makineye özel yolu göreli hale getir

- cd '/Users/hakan/Documents/GitHub/logo_2026_microservice'
+ cd /path/to/your/checkout

Tercihen README’de depoya göreli komutları doğrudan kullanın; bu yol mevcut depo diziniyle de aynı görünmüyor.

E · Elasticsearch güvenliği kapalıyken gereksiz parola env’ini kaldır

-      - ELASTIC_PASSWORD=logo123

Compose’ta xpack.security.enabled=false; ELASTIC_PASSWORD burada çalışan kimlik doğrulaması sağlamaz. Gerçek kimlik doğrulama etkinleştirilecekse TLS, secret yönetimi ve client ayarları birlikte tasarlanmalıdır.

Eğitmen onayı: Önerileri gerçek projeye uygulamadan önce servis sahipleriyle endpoint maruziyetini, compatibility testlerini, /data izinlerini ve güvenlik gereksinimlerini onaylayın. Atölye, bu diff’leri mevcut uygulama dosyalarına uygulamaz.

Bu makinede doğrulama durumu

  • Görülen CLI sürümleri: kubectl client v1.37.1, Helm v4.2.3; kubeconfig current-context: rancher-desktop.
  • Cluster API https://127.0.0.1:6443 bağlantıyı reddetti. Dolayısıyla Traefik, metrics-server, local-path StorageClass ve NetworkPolicy’nin bu cluster’da etkinliği çalıştırılarak doğrulanmadı. Ortam rehberindeki kontroller cluster açıldıktan sonra uygulanır.
  • Docker daemon da erişilemiyor. Registry manifest index’leri sorgulandı: Eclipse Temurin 17, Redis 7.2, Confluent Kafka/Zookeeper 7.6.0, Elastic 8.13.0 ve Kafka UI `latest` linux/amd64 + linux/arm64 yayınlıyor. Redis Commander `latest` tek platform manifesti; ARM64 desteği doğrulanmadı, eğitim manifestine alınmamıştır. `latest` etiketi sabitlenmiş üretim sürümü değildir.
  • Server-side dry-run API erişimi yüzünden çalıştırılamadı. kubectl apply --dry-run=client --validate=false denemeleri de API discovery bağlantısı gerektirdiğinden aynı nedenle başarısız oldu. Helm chart lint/render edildi; Helm dışındaki 29 YAML/patch dosyası yerel YAML parser’ından geçti. Cluster açıldığında tüm manifestler için kubectl apply --dry-run=server çalıştırılmalıdır.
