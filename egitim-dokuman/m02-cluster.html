m02 · Cluster yapısı, kubectl ve namespace

Kontrol düzlemi istenen durumu yönetir; worker node uygulama Pod’larını çalıştırır. Tek node’lu Rancher Desktop’ta ikisini aynı yerel makine üzerinde görebiliriz.

1. Hedef ve çıktı

kubectl’i doğru rancher-desktop context’ine bağlayın, node/kube-system kaynaklarını inceleyin ve `logo-ms` namespace’ini oluşturun. Çıktı: namespace `Active`, node `Ready` ve cluster sürüm/architecture bilgisi not edilmiş.

2. Kurumsal katkı

Yanlış context, eğitim kaynağını üretime deploy etmeye yol açabilir. Apply öncesi context/namespace kontrolü olayın etki alanını küçültür. Namespace’ler ekip sahipliği, RBAC kapsamı ve kaynak kotası ayırmaya yardımcı olur; tek başına ağ güvenlik duvarı veya tam tenant sınırı değildir. NetworkPolicy ve RBAC ayrı kontrollerdir.

3. Kavram

Kontrol düzlemi (control plane) API server, scheduler, controller manager ve etcd bileşenlerinden oluşur. Worker node üzerinde kubelet, container runtime ve ağ bileşenleri çalışır. API server kimliği doğrulanmış isteklerin girişidir; scheduler yerleşmemiş Pod için node seçer; controller’lar gerçek durumu istenen duruma yaklaştırır; etcd API durumunu saklar. kubectl clusterın kendisi değil, API istemcisidir. Benzetme: API server hizmet masası, etcd kayıt defteri, scheduler oda atayan görevli, kubelet işi uygulayan ekiptir.

Cluster (küme), node (düğüm), namespace (ad alanı) ve context (küme + kullanıcı + varsayılan namespace) farklı kavramlardır. Rancher Desktop context allows a single-node practice environment; Tek node ile control plane yüksek erişilebilirliği (HA) gösterilemez.

4. Proje senaryosu

Eğitim objelerinin tümü `logo-ms` namespace’ini hedefler; depodaki referans manifestler de aynı namespace’i kullanır. `logo/*` uygulama image’larını yerel runtime’a yükleyin ve eğitim context’ini kurumsal cluster’a yönlendirmeyin. İlk namespace manifesti: namespace.yaml.

5. Adım adım komutlar

  1. Confirm CLI versions/context. If context is not rancher-desktop stop; don't apply.
  2. Cluster ve node label/mimari bilgilerini, ayrıca sistem Pod’larını inceleyin.
  3. Apply the training namespace; Namespace’leri listeleyin ve kısa komutlar için kabukta varsayılan namespace’i ayarlayın.
  4. Compare namespace visibility with `-A` and explicit `-n logo-ms`.

6. YAML açıklaması

Namespace manifestinde `apiVersion: v1` core API grubunu, `kind: Namespace` kaynak türünü, `metadata.name: logo-ms` namespace adını belirler. Namespace cluster-scope bir kaynaktır; namespaced objelerden önce oluşturulur. Namespace kaynağının kendi metadata’sında `namespace` alanı bulunmaz.

apiVersion: v1
kind: Namespace
metadata:
  name: logo-ms

Apply the Namespace first because Kubernetes cannot create a Deployment in a namespace that doesn't exist unless your workflow creates it explicitly.

7. macOS ve Windows farkları

Paths with spaces need quotes; this YAML path has no spaces. zsh/macOS uses ./ for local executables, PowerShell uses .\; kubectl syntax is the same. PowerShell line continuation is backtick (fragile trailing spaces), zsh is backslash; type each example as one line. JSONPath braces must be quoted in PowerShell when shell parsing interferes.

8. Eğitmen notları

Say: “kubectl speaks to the API; it does not start a VM itself.” Show: current context, node, system pods, one namespace manifest. Duration: 25 min. Stop and ask: “What prevents this namespace from being a security boundary?” Expected: RBAC and NetworkPolicy are separate; namespace alone is not enough.

Likely questions: etcd database; scheduler selects a node; k3s packages control-plane services for small distributions. Trap: `get pods` with no namespace can hide system context, or default context can point elsewhere. Don't apply until context and server endpoint are confirmed.

9. Katılımcı alıştırması

Write down node name, OS/architecture, Kubernetes client version and active namespace. Apply namespace and check its status. Hint: namespace doesn't appear in `get pods`; query namespaces directly.

Verify with kubectl get namespace logo-ms and kubectl get nodes -o wide.

Show solution

Beklenen durum: namespace `Active`, yerel node `Ready`; mimari arm64 veya amd64 olabilir. Context’i `kubectl config current-context` ile doğrulayın. Node adı/IP ve server sürümü katılımcının Rancher Desktop sürümüne bağlı olduğundan önceden sabitlenmemiştir.

10. Sık hatalar ve çözümleri

  • Connection refused: Rancher Desktop cluster API isn't Ready; wait for Ready and repeat `get nodes`.
  • Forbidden: identity lacks RBAC permission; don't switch to cluster-admin as a workaround.
  • Namespace NotFound: apply 00 namespace first; verify exact spelling `logo-ms`.
  • Wrong cluster: stop, read context/endpoint, then choose the approved lab context.

11. Üretimde fark

Üretim ortamında birden çok control-plane node’u, ayrı worker havuzları, HA etcd, kimlik entegrasyonu, audit logları, kontrollü context erişimi ve ekip namespace’leri bulunur. Tek node k3s API/reconciliation öğretir ancak node/zone arızasını, control-plane quorumunu veya kurumsal kimliği kanıtlamaz.

12. Modül özeti ve kontrol listesi

  • Correct context and node architecture checked.
  • `logo-ms` namespace active.
  • Can explain API server, scheduler, etcd and kubelet roles.
  • Understand namespace is not sufficient network isolation.
