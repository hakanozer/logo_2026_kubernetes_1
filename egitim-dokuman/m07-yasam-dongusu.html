Güvenli release

m07 · Rolling update, rollback, scale ve probes

Order deployment’ını denetimli güncelleyin, rollback edin; self-healing’i gözleyin ve health probe tiplerini doğru ayırın.

1. Hedef ve somut çıktı

Order’ın Pod sayısını artırıp azaltın; eğitim amaçlı aynı binary’yi v1/v2 tag’leriyle build ederek rollout revision ve rollback gösterin; hatalı tag’den geri dönün; Pod silinince otomatik yeniden oluşmasını doğrulayın. Actuator bağımlılığı eğitmen onayı gerektirdiğinden probe manifesti, Actuator hazır olmadıkça uygulanmaz.

2. Kurumsal katkı

Rolling update kapasiteyi kademeli yeniler; readiness probe, trafik almaya hazır olmayan Pod’u Service uç noktalarının dışında tutar. Revision ve rollback önceki sürüme dönüş yolu sağlar. Self-healing, elle müdahaleye kadar geçen süreyi azaltır. Liveness yanlış ayarlanırsa sürekli yeniden başlatma; readiness yanlışsa trafik kaybı; startup probe yoksa yavaş başlayan JVM’in erken öldürülmesi görülebilir. Doğru sağlık kontrolleri dağıtım riskini ve planlı kesinti ihtiyacını azaltır.

3. Kavram

Rolling update = eski Pod’ları kademeli yeni Pod’larla değiştir; maxSurge/maxUnavailable hız ve kapasiteyi sınırlar. Rollback eski ReplicaSet revision’a dönüş. Scaling desired replica count; self-healing controller reconciliation. Startup probe uygulama başlatma süresince diğer probe’ları bekletir; liveness “process restart gerekli mi?”; readiness “şu anda request alabilir mi?”. Spring Boot Actuator ekli değilse `/actuator/health` endpoint’i varsaymayın.

4. Proje senaryosu

H2 Order replica scaling data consistency riski doğurur: her Pod aynı PVC’yi paylaşan H2 file instance olmaz; tek H2 file için iki replica desteklenen HA çözümü değildir. Atölyede scaling mekanizmasını izole etmek için Order replicas’ını kısa süreli artırıp persistence side effect’i tartışın; sonra tek replica’ya dönün. Safer stable scaling demo Gateway stateless service. v1/v2 image’ları aynı kaynak koddan üretildiği için yalnızca rollout mekanizmasını gösterir; uygulama davranışı değişmez. Probe alıştırması yalnızca Actuator kod değişikliği onaylandıktan sonra uygulanır.

5. Adım adım uygulama

  1. Order v1/v2 gösterimi için `bash egitim-k8s/07-rollout/build-demo-tags.sh containerd` veya `... dockerd` komutuyla aynı kaynak kodundan iki etiket üretin. Bu, rollout mekanizmasını gösterir; uygulama işlevi değişmez.
  2. Başlangıç image’ını, generation’ı ve replica sayısını kaydedin; `kubectl set image` ile v2’ye geçip rollout durumunu ve ReplicaSet revision’larını izleyin. Hatalı image etiketini yalnızca ayrı arıza alıştırmasında kullanın ve hemen geri alın.
  3. Gateway’i ölçekleyin, bir Pod silip controller’ın yenisini oluşturduğunu görün ve başlangıç replica sayısına dönün. Mevcut image’larda Actuator yoktur. Eğitmen onaylı POM diff’i ve yeniden build tamamlandıktan sonra kubectl patch deployment/api-gateway --type=strategic --patch-file=egitim-k8s/07-rollout/actuator-probes.patch.yaml -n logo-ms ile probe örneğini uygulayın. 6. YAML açıklaması

Deployment `strategy.type: RollingUpdate`; `rollingUpdate.`maxSurge` istenen replika sayısının üzerinde izin verilen ek Pod sayısını tam sayı veya yüzde olarak belirtir; `maxUnavailable` caps unavailable count. Container `readinessProbe` gates endpoint membership; `livenessProbe` may restart; `startupProbe` defers others. HTTP probe; `path`, `port`, `initialDelaySeconds`, `periodSeconds`, `timeoutSeconds` ve `failureThreshold` alanlarını kullanır. `apiVersion: apps/v1` stable Deployment. Readiness path must exist and not redirect to login.

Example only after Actuator included/approved:

startupProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 5
  failureThreshold: 24
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: http
  periodSeconds: 5

Mevcut servislerde Actuator bağımlılığı yoktur; bu probe’u şimdiki image’a eklerseniz endpoint 404 döner ve Pod Ready olmaz.

7. macOS ve Windows farkları

kubectl syntax common. Container build path has spaces and needs quotes. In PowerShell 5, `curl` maps to Invoke-WebRequest, so use `curl.exe`. To run the same v1/v2 build commands through multiple shells, type separately and keep container engine consistent.

8. Eğitmen notları

Say: “Kubernetes can return an old Pod template; it cannot undo a database migration.” Show: ReplicaSet counts and rollout history, then liveness/readiness difference diagram. Duration: 50 min. Stop: “Should readiness failure restart the process?” No, it removes it from traffic; liveness controls restart.

Be honest: v1/v2 tags are identical binary if no code modification is approved. It proves Deployment mechanics, not a business change. Do not use shared H2 Order data for multi-replica production claims. Actuator and probe path are not present by default.

9. Katılımcı alıştırması

Perform a controlled Gateway scale from 1→3→1, delete one Gateway Pod, observe replacement. For Order rollout, change tag to v2 then undo. Capture deployment generation and revision.

Verify with `kubectl rollout status`, `kubectl get rs,pods -l app=api-gateway` and `kubectl rollout history`.

Show solution

Set desired replicas to 3; see three pods; delete one selected Gateway Pod and confirm new Pod name/UID but same desired total. For Order, the template tag change creates a new revision; `rollout undo` returns previous tag. Product-level difference requires a real v2 application image. Current code's health endpoint is not available until Actuator change is approved and built.

10. Errors and solutions

  • ProgressDeadlineExceeded: image, readiness, quota and events.
  • Pod restart loop after probe: inspect endpoint and timing; current code likely lacks Actuator.
  • Revision no-op: ensure pod template changed; image tag must differ.
  • Order replica data anomalies: H2 file DB is not safe shared clustered storage; revert one replica.

11. Üretimde fark

Rollouts add canary/blue-green, automated SLO gates, PDB and topology spread; health checks distinguish dependency degradation from process health. DB migrations use expand/contract strategies; rollback needs compatible schema. Autoscaling and surge need reserved node capacity. Local exercise doesn't prove zero-downtime, because single-node resource contention and load are uncontrolled.

12. Modül özeti ve kontrol listesi

  • Scale and self-healing visible.
  • Image template change produced revision and undo worked.
  • Startup, liveness and readiness roles correctly distinguished.
  • Actuator is explicitly marked prerequisite, not falsely assumed.
