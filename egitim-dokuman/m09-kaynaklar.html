m09 · Requests, limits, HPA, VPA ve Cluster Autoscaler

İş yükleri için kaynak bütçesi belirleyin; HPA’yı metrics-server ile deneyip Kafka partition sınırını throughput tartışmasına bağlayın.

1. Hedef ve çıktı

Gateway ve Payment’e requests/limits verin; metrics API ve `kubectl top` doğrulayın; HPA ile replica değişimini yük altında gözleyin. Payment scaling’in partition ve concurrency nedeniyle neden otomatik throughput artışı olmadığını kanıtlayın. VPA/Cluster Autoscaler’ı üretim topolojisi diyagramıyla açıklayın.

2. Kurumsal katkı

Requests scheduler’ın kapasite taahhüdünü, limits container kullanım tavanını belirler. Requests eksikse bin-packing/overcommit ve noisy neighbor; limits yanlışsa throttling/OOM ve hizmet gecikmesi oluşur. HPA demand’a göre uygulama kopyası ekler, fixed overprovision maliyetini azaltır; doğru metrics ve partition/concurrency kapasitesi olmazsa Pod sayısı sadece maliyet/kafka bağlantısı ekler.

3. Kavram

CPU request millicore; CPU limit throttling tavanı. Memory request scheduling; memory limit aşımı OOM kill’e yol açabilir. HPA workload replica scale yapar; VPA Pod request/limit önerir veya günceller (mode/eviction policy’ye bağlı). Cluster Autoscaler uygun Pod’lar node’a sığmadığında cloud node group’u büyütür; scale-down boş node’u kaldırır. Tek local node’da gerçek node scaling yok.

4. Proje senaryosu

Referans K8s’te resources/HPA yok. `payment-service` event listener 3 saniye sleep yapar ve custom Kafka listener factory concurrency açıkça ayarlı değildir; broker/topic partition sayısı tüketici paralelliğini sınırlar. Topic 1 partition ise aynı consumer group’ta en fazla bir consumer partition assignment alır; 3 partition ve uygun consumer concurrency ile üçe kadar paralellik teorik olur. Producer key/group behavior ve backpressure de ölçülmelidir. HPA CPU metric tek başına kafka lag autoscaling değildir.

5. Uygulama

  1. Önce Metrics API’nin ve hedef Deployment’ların hazır olduğunu doğrulayın. HPA v2 CPU yüzdesini `requests.cpu` değerine göre hesaplar; HPA’dan önce şu kaynağı uygulayın: `kubectl set resources deployment/api-gateway deployment/payment-service --requests=cpu=100m,memory=128Mi --limits=cpu=500m,memory=512Mi -n logo-ms`.
  2. Ardından `kubectl apply -f egitim-k8s/09-resources/hpa.yaml` ile Gateway ve Payment HPA’larını kurun. Yükü sınırlı tutmak için `kubectl run load-generator -n logo-ms --image=busybox:1.36 --restart=Never -- /bin/sh -c 'while true; do wget -q -O /dev/null http://api-gateway:8080/inventory/list; done'` ile istek üretin; yaklaşık 1–2 dakika sonra `kubectl delete pod/load-generator -n logo-ms` ile durdurun.
  3. `kubectl top`, HPA current/desired replica ve event’lerini gözlemleyin; örnek toplanması ve ölçekleme dakikalar alabilir. Payment replikalarını değiştirmeden önce Kafka partition sayısını, consumer group atamalarını ve lag’i kontrol edin. Pod sayısı artışı tek partition üzerinde paralel tüketim anlamına gelmez.
  4. VPA ve Cluster Autoscaler’ı kavramsal anlatın; tek node’lu yerel cluster’a bulut node autoscaler kurmayın. Gerçek node ölçeklemesi için çoklu node ve cloud provider entegrasyonu gerekir.

6. YAML açıklaması

Container `resources.requests` required scheduler reservation; `limits` cap. HPA `apiVersion: autoscaling/v2`; `scaleTargetRef` exact Deployment API/name; `minReplicas/maxReplicas`; `metrics[].resource.name: cpu`; `averageUtilization` percentage of CPU request; `behavior` stabilization/rate policies. HPA, Deployment replica sayısını ayarlar; CPU/bellek değerlerini değiştirmez. VPA için CRD ve controller gerekir; Pod’ları güncelleyebilir veya tahliye edebilir. Cluster Autoscaler için desteklenen bulut sağlayıcısı, node group ve gerekli izinler gerekir.

7. macOS / Windows farkı

kubectl komutları macOS ve Windows’ta aynıdır. Windows yük döngüsünde `curl.exe`, PowerShell beklemesinde `Start-Sleep` kullanılır. Sınırsız döngü çalıştırmayın; süre/hızı sınırlayın ve Ctrl+C ile durdurun. Image mimarisi node mimarisiyle eşleşmelidir. Tek node CPU’su sınırlı olabilir ve ana işletim sistemini de yavaşlatabilir.

8. Eğitmen notları

Say: “Request scheduling reservation; limit enforcement boundary.” Show: top vs request; HPA conditions; topic partitions vs members. Duration: 45 min. Stop: “Five Payment Pods means five active partition readers?” Tek partition veya tek consumer concurrency varsa daha fazla Payment Pod’u tek başına tüketim hızını artırmaz.

Yük üretimini sınırlayın ve dizüstü bilgisayar kaynaklarını izleyin. Mevcut Payment custom listener factory’si concurrency değerini açıkça ayarlamıyor; `application.yml` içindeki genel concurrency değeri özel factory’ye uygulanmayabilir. Varsayım yerine aktif consumer üyelerini kontrol edin. metrics-server yoksa diyagram/YAML ile anlatın; sahte HPA çıktısı üretmeyin.

9. Katılımcı alıştırması

Run Gateway with a sustained bounded load; observe HPA response. Then compare Payment group with one vs three partitions/replicas. Record active members and throughput; stop load process and return to baseline replicas.

Verify `kubectl top pods`, `kubectl get hpa`, `kubectl describe hpa`, broker topic description and consumer group tooling/lag.

Show solution

Set CPU requests, ensure metrics API and HPA are active, then generate enough continuous CPU load long enough for sampling/stabilization. HPA may remain at one if the proxy workload is light. Payment scaling only yields concurrency up to assigned partitions and configured listener concurrency; single partition leaves surplus consumers idle. Return HPA/replicas and stop load generator.

10. Errors and solutions

  • HPA target unknown: check metrics-server API and resource requests.
  • Replica count unchanged: load insufficient/short, maxReplicas hit, quota/capacity, or behavior stabilization.
  • OOMKilled: inspect memory usage/limit, not CPU HPA alone.
  • Payment scales but no throughput: inspect topic partition count, consumer group assignment, lag and listener concurrency.

11. Üretimde fark

Üretim kapasite planı yük testinden alınan requests, SLO, JVM heap/cgroup memory, burst/throttling, node rezervasyonu, quota, HPA metrik seçimi (queue lag gibi custom metric), VPA çalışma modu, Cluster Autoscaler node havuzu, zone ve bekleme sürelerini kapsar. VPA ve HPA aynı CPU/memory kaynağını değiştiriyorsa çakışmayı çözün. Tek node cloud LB veya Cluster Autoscaler davranışını gösteremez.
