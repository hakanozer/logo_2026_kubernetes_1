Least privilege

m10 · RBAC, ServiceAccount, Pod security ve image güvenliği

Bir workload identity’ye salt-okunur yetki verin; root olmayan container, SecurityContext ve Pod Security Standards katmanlarını uygulama sırasıyla öğrenin.

1. Hedef ve çıktı

ServiceAccount + namespace Role/RoleBinding ile yalnızca Pod/Service okuyan principal oluşturun; `can-i` ile izin/ret test edin. Non-root image/securityContext kurgusu, PSS label’ları, Secret ve registry digest/image scanning zincirini açıklayın. Çıktı: least-privilege RBAC check; security setting uygulanabilirliği belgelenmiş.

2. Kurumsal katkı

Uygulama kimlik bilgisinin ele geçirilmesi cluster-admin yetkisi vermemelidir. En az ayrıcalıklı RBAC, platforma yayılabilecek zararı sınırlar; namespace kapsamı ve kısa ömürlü ServiceAccount token’ları kimlik bilgisinin kullanım süresini azaltır. Root olmayan kullanıcı ve capability kısıtları container açığının etkisini düşürür. Image taraması ve digest/provenance, bilinen zafiyetleri ve etiket değişikliği riskini azaltır. PSS ve admission policy’leri denetlenebilir bir taban sağlar. Volume izinleri ve ayrıcalıklı çalışma gereksinimleri sınanmamışsa güvenlik kontrolleri iş yükünü bozabilir.

3. Kavram

Kubernetes güvenlik katmanları: kimlik doğrulama, RBAC yetkilendirme, admission kontrolleri, ağ, workload çalışma zamanı, image tedarik zinciri, Secret/veri şifreleme ve audit. ServiceAccount Pod’un API kimliğidir. Role namespace içinde resource/verb izinlerini, RoleBinding bu rolün bağlandığı kimliği tanımlar. SecurityContext UID/GID, capability ve filesystem seçeneklerini belirler. PSS baseline/restricted Pod güvenlik standartlarıdır; namespace `enforce`, `audit`, `warn` etiketleri admission davranışını seçer.

4. Proje senaryosu

Mevcut `dashboard-admin-user` binding’i `cluster-admin` verir (yalnızca referans manifestinde bulunur, eğitimde yeniden kullanılmaz). Referans workload’lar root yetkili Dockerfile ve düz metin kimlik bilgileri kullanır. `imagePullPolicy: Never` image bütünlüğünü doğrulamaz. Eğitim manifesti namespace kapsamlı salt-okunur Role kullanır; Dockerfile’ları root olmayan kullanıcıya geçirme önerisi eğitmen onayı bekler, otomatik uygulanmaz.

5. Uygulama

  1. `kubectl apply -f egitim-k8s/10-security/rbac.yaml` ile eğitim ServiceAccount’ını, yalnızca Pod/Service için get/list/watch izni veren Role’u ve RoleBinding’i oluşturun; Role kurallarını inceleyin.
  2. kubectl auth can-i ile get pods izninin verildiğini ve create deployments izninin reddedildiğini sınayın. Bu kontrolü cluster-admin kimliğiyle yapmayın.
  3. restricted-pod.yaml içindeki runAsNonRoot, runAsUser, allowPrivilegeEscalation: false, tüm capability’leri düşürme, seccompProfile: RuntimeDefault ve readOnlyRootFilesystem ayarlarını inceleyin. Yazılabilir dizinler için açık volume mount gerekir.
  4. Namespace’e önce PSS warn/audit etiketleri uygulayın; yalnızca workload image’ları ve volume yolları kontrol edildikten sonra enforce=restricted kullanın. Mevcut namespace’i körlemesine restricted yapmayın.
  5. Image’ı kurumun onayladığı scanner ile tarayın; dağıtım girdisi olarak tag yerine digest kaydedin, provenance/imza doğrulamasını tartışın.

6. YAML açıklaması

Role `apiVersion: rbac.authorization.k8s.io/v1`; `rules` list `apiGroups` (core is empty string), `resources`, and minimum `verbs`; RoleBinding `roleRef` exact Role and `subjects` serviceAccount namespace. Pod `serviceAccountName` binds identity. `automountServiceAccountToken: false` when app doesn't call API. `runAsNonRoot` and numeric UID; `allowPrivilegeEscalation: false`; `capabilities.drop: [ALL]`; `seccompProfile.type: RuntimeDefault`. PSS namespace label `pod-security.kubernetes.io/enforce` is admission policy, not a runtime context.

7. macOS / Windows

RBAC/YAML commands identical. Image build engine follows machine configuration. macOS Apple Silicon images should match arm64 node; Windows WSL2 build image may be linux/amd64 or arm64 depending host. Use `kubectl get nodes -o wide` architecture. Scanner installation and registry auth follow organization endpoint; never paste credentials into PowerShell/zsh shell history.

8. Eğitmen notları

Say: “Bir uygulama kimliğine, platformu yönetme yetkisi vermiyoruz.” Show: `can-i yes/no`, restricted context diagram, image digest vs tag. Duration: 50 min. Stop: “Namespace restricted enforce etiketini şimdi uygulayalım mı?” Önce non-root image ve volume izinlerini doğrulayın.

Reference `dashboard-admin-user.yaml` cluster-admin is not a training template for apps. Avoid printing Secret content. Rootless UID can make H2 /data unwritable; security controls need coupled image/volume changes and review.

9. Katılımcı alıştırması

Show reader can `list pods` but cannot `create deployments`. Add RoleBinding only in logo-ms; verify another namespace scope is not granted. Examine `kubectl auth can-i` and `kubectl describe rolebinding`.

Hint: Role verbs and resource group must both match exact API operation.

Show solution

Role permits `get,list,watch` only on core Pods/Services; RoleBinding refers to `logo-reader` SA in `logo-ms`. `list pods` says yes, `create deployments` says no. Namespace Role doesn't grant permissions in other namespaces. If impersonation is denied, the human caller lacks impersonate privilege; do not broaden reader role as a workaround.

10. Sık hatalar ve çözümleri

  • Forbidden: check `kubectl auth can-i`, namespace and exact verb/resource.
  • runAsNonRoot failure: image declares root user; rebuild/pin numeric non-root UID.
  • permission denied on /data: set volume ownership/fsGroup and validate DB write.
  • PSS violation: start warn/audit, fix reported field, then consider enforce.

11. Üretimde fark

Integrate external identity, workload identity, admission policy, image signing/SBOM/scanning, registry allowlist, digest pinning, rotation/encryption of secrets, network policy and audit. Never grant `cluster-admin` to microservice. VEX and exception records should be time-bound. K8s Pod Security Standards do not replace runtime detection or a threat model.

12. Modül özeti ve kontrol listesi

  • ServiceAccount uses least-privilege Role.
  • `can-i` allow/deny both tested.
  • Non-root and writable mount requirements reviewed together.
  • PSS warn/audit before enforce; scan and digest are distinct controls.
